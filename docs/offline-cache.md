# 离线缓存（播放缓存 + 歌词缓存）

> 目标：**一首歌播放成功后，下次播放不再请求远程**；即使源失效/断网，也能正常播放与看歌词。

## 一、决策（已确认）

| 项 | 结论 |
|---|---|
| 与「已下载」的关系 | **分开**：独立缓存目录、**不写** `Song.localPath`（「已下载」语义不变） |
| 触发范围 | **仅「播放成功」的歌** |
| 容量 | **不设上限**，只提供手动清空 |
| 开关 | 设置页「播放时自动缓存」，**默认开启** |
| 缓存引擎 | **乙**：起播后后台另下一份；`.part` 临时名，**完整后才算命中** |
| 网络 | 不区分网络（不联动 wifiOnly） |
| 已下载的歌 | **不重复存**，直接用 `localPath` 播放 |
| 离线范围 | 播放 + 歌词 + 列表快照 |
| 歌词缓存 | **始终开**（无开关），且**在播放时就开始**（不是打开歌词页才请求） |
| 附加 | 列表/播放条显示「离线可用」标记；不做按时间自动清理 |

## 二、目录与命名

* 根目录：`getApplicationSupportDirectory()/audio_cache/`（**持久目录**；临时目录会被系统清理，达不到「下次还能播」）
* 文件：`<sourceId>/<清洗后的 globalKey>.mp3`，下载中为同名 `.part`
* **命中规则：只有完整文件（无 `.part` 后缀且大小 > 0）才算命中**
  —— 这是「乙」的关键保险：绝不把半截文件当缓存播（`progressive_video_cache` 走的是「播增长中文件」，在 just_audio/Windows 上不可控，故不采用）

## 三、数据流

1. **播放地址解析**（点播 / 上一首 / 下一首 / 跳转 / 自动续播都走同一处）
   ① 有 `localPath`（用户已下载）→ 用它，且**不再另存缓存**
   ② 音频缓存命中 → `file://<完整文件>`，**完全不请求源**
   ③ 否则 → `SourceManager.getPlayable`（顺带拿元数据）→ 起播成功后触发缓存
2. **歌词**：曲目开始播放时（`currentSongStream` 唯一漏斗）→ `ensureLyrics` 异步取词并写入 `songs.lyric`
   * 展示层只读缓存：命中直接用（**零远程请求**）；未命中才问源（兼容历史曲目）
   * 同一首的并发请求按 key 去重（播放触发与打开歌词不会打两次）
3. **列表快照**：`recent_plays` / `favorites` 均有 `title/artist/cover_url` 快照列，源失效时按快照渲染，不依赖 `songResolver`

## 四、开关与清理

* 设置键：`audio_cache_play`（`'1'`/`'0'`，缺省视为开）
* 设置页：开关 + 显示占用体积 + 「清空播放缓存」（删文件但不动 `localPath`）
* 关闭开关：只停止**新的**缓存写入，已缓存文件仍可用于播放（不静默删除用户既有数据）

## 五、预留：升级到「甲」（1 倍流量）

播放器已支持 `StreamAudioSource`（just_audio 内部由本地 HTTP 代理承载，Windows 亦可用）。
现在就把「取音源」收敛成一个可替换的 `audioSourceBuilder`（v1 = `AudioSource.uri`）；
将来做甲，只需把它换成基于 `StreamAudioSource` 的实现（边转发边落盘），
**缓存目录、命名、命中、开关、清理全部复用，不需改动**。

## 六、验收（端到端）

1. 播放一首 → `audio_cache` 出现完整文件；`songs.lyric` 已写入（**全程不打开播放页/不开歌词**）
2. **停用该源 + 重启 App** → 再点同一首：**能播**（日志出现 `file://`，**没有** `播放URL` 请求）
3. 打开歌词：**仍有词，且没有歌词请求**
4. 列表显示「离线可用」标记
5. 对照组：没播过的歌，停用源后如实失败 / 歌词为空（不造假）
6. 设置页：占用显示正确；清空后重播会重新缓存
